# SkillBridge Notifications: Frontend Integration Guide

This document describes the current backend notification contract for frontend developers.

## 1. What Notifications Do

A notification is created when a student books a service or when an admin approves a tutor's service revision.

The notification is sent for these approval cases:

- A new service is approved (`CREATE` revision).
- An existing service update is approved (`UPDATE` revision).
- A service deletion revision is approved (`DELETE` revision).
- A student books a service (`SERVICE_BOOKED`, sent to the tutor).
- An upcoming service is updated and approved (`SERVICE_UPDATED`, sent to students booked for that service).

Rejections currently do not create notifications.

Notifications are both:

1. Persisted in the database, so they are available when the tutor is offline.
2. Sent in realtime over the existing per-user chat WebSocket when the tutor is online.

The REST API is the source of truth. WebSocket messages should be treated as realtime updates, not as the only way to load notifications.

## 2. Base URLs

The API prefix is configured by the backend and is currently `/v1`.

Examples below assume:

```text
REST:      https://api.example.com/v1
WebSocket: wss://api.example.com/v1
```

For local development, replace the host and protocol with the backend's local URL. Use `wss://` in production and `ws://` locally when TLS is not configured.

## 3. Authentication

All notification REST endpoints require the same bearer access token used by the rest of the application:

```http
Authorization: Bearer <access_token>
```

The backend gets the authenticated user ID from the JWT. The frontend must not send another user's ID to retrieve notifications; the server scopes results to the authenticated user.

## 4. Notification Object

A notification has this shape:

```json
{
  "id": "notification-uuid",
  "user_id": "tutor-user-uuid",
  "notification_type": "SERVICE_BOOKED",
  "title": "New service booking",
  "message": "A student booked your service 'Python tutoring'.",
  "data": {
    "booking_id": "booking-uuid",
    "service_id": "service-uuid",
    "student_id": "student-profile-uuid"
  },
  "is_read": false,
  "created_at": "2026-09-13T12:00:00+00:00"
}
```

Fields:

| Field | Type | Meaning |
| --- | --- | --- |
| `id` | UUID string | Unique notification ID. Use this as the frontend list key and read endpoint ID. |
| `user_id` | UUID string | User account receiving the notification. |
| `notification_type` | string | `SERVICE_BOOKED`, `SERVICE_APPROVED`, `SERVICE_REVISION_APPROVED`, or `SERVICE_UPDATED`. |
| `title` | string | Display title. Currently `Service approved`. |
| `message` | string | Display message generated by the backend. |
| `data` | object or `null` | Context for navigation and refresh actions. |
| `is_read` | boolean | Current read state. New notifications are `false`. |
| `created_at` | datetime string or `null` | Creation time. Sort/display using this value when present. |

The `data` object currently contains:

```json
{
  "revision_id": "revision-uuid",
  "service_id": "service-uuid-or-null",
  "revision_type": "CREATE"
}
```

For a `CREATE` approval, `service_id` is assigned when the approved service is created. For `UPDATE` and `DELETE`, it refers to the existing service when available.

Booking notifications use `booking_id`, `service_id`, and `student_id`. `SERVICE_UPDATED` notifications use `revision_id`, `service_id`, and `revision_type`. Student update notifications are created only for approved updates whose resulting service date/time is still upcoming.

## 5. List Notifications

### Request

```http
GET /v1/notifications/?limit=50&offset=0&unread_only=false
Authorization: Bearer <access_token>
```

Query parameters:

| Parameter | Default | Rules |
| --- | --- | --- |
| `unread_only` | `false` | Set to `true` to return only unread notifications. |
| `limit` | `50` | Minimum `1`, maximum `100`. |
| `offset` | `0` | Must be `0` or greater. |

### Response

```json
{
  "success": true,
  "message": "Notifications fetched.",
  "metadata": {
    "total": 12,
    "unread_count": 3,
    "limit": 50,
    "offset": 0
  },
  "data": [
    {
      "id": "notification-uuid",
      "user_id": "tutor-user-uuid",
      "notification_type": "SERVICE_APPROVED",
      "title": "Service approved",
      "message": "Your service 'Python tutoring' was approved.",
      "data": {
        "revision_id": "revision-uuid",
        "service_id": "service-uuid",
        "revision_type": "CREATE"
      },
      "is_read": false,
      "created_at": "2026-09-13T12:00:00+00:00"
    }
  ]
}
```

Notifications are returned newest first. `total` is the number of records matching the current filter. `unread_count` is the user's total unread count, even when `unread_only=true` is used.

Recommended initial page load:

1. Request `GET /notifications/?limit=50&offset=0`.
2. Store the returned list and `metadata.unread_count`.
3. Open the WebSocket for realtime events.

## 6. Mark One Notification as Read

### Request

```http
PATCH /v1/notifications/{notification_id}/read/
Authorization: Bearer <access_token>
```

No request body is required.

### Successful response

```json
{
  "success": true,
  "message": "Notification marked as read.",
  "metadata": {},
  "data": {
    "id": "notification-uuid",
    "user_id": "tutor-user-uuid",
    "notification_type": "SERVICE_APPROVED",
    "title": "Service approved",
    "message": "Your service was approved.",
    "data": {},
    "is_read": true,
    "created_at": "2026-09-13T12:00:00+00:00"
  }
}
```

The operation is idempotent. Marking an already-read notification as read is safe.

A notification belonging to another user returns `404`, rather than exposing it.

## 7. Mark All Notifications as Read

### Request

```http
PATCH /v1/notifications/read-all/
Authorization: Bearer <access_token>
```

No request body is required.

### Response

```json
{
  "success": true,
  "message": "Notifications marked as read.",
  "data": {
    "updated_count": 3
  }
}
```

Calling this endpoint again is safe and returns `updated_count: 0` when no unread notifications remain.

## 8. WebSocket Realtime Delivery

Notifications use the same WebSocket connection currently used by chat:

```text
GET /v1/chat/ws/{user_id}
```

Example:

```javascript
const socket = new WebSocket(
  `wss://api.example.com/v1/chat/ws/${currentUser.id}`
);

socket.onmessage = (event) => {
  const frame = JSON.parse(event.data);
  console.log(frame.event, frame.payload);
};
```

When a booking or service approval notification is created, the server sends:

```json
{
  "event": "notification",
  "payload": {
    "id": "notification-uuid",
    "user_id": "tutor-user-uuid",
    "notification_type": "SERVICE_BOOKED",
    "title": "New service booking",
    "message": "A student booked your service 'Python tutoring'.",
    "data": {
      "booking_id": "booking-uuid",
      "service_id": "service-uuid",
      "student_id": "student-profile-uuid"
    },
    "is_read": false,
    "created_at": "2026-09-13T12:00:00+00:00"
  }
}
```

The notification payload has the same shape as the REST notification object. The frontend can insert it into the local list and increment the unread badge.

Recommended actions by notification type:

| Type | Recipient | Suggested action |
| --- | --- | --- |
| `SERVICE_BOOKED` | Tutor | Open the service or bookings view. |
| `SERVICE_APPROVED` | Tutor | Open the approved service. |
| `SERVICE_REVISION_APPROVED` | Tutor | Open the updated service. |
| `SERVICE_UPDATED` | Booked student | Open the booked service/session and refresh its schedule/content. |

The existing WebSocket also emits chat events such as `new_message`, `history`, `read_receipt`, `typing`, and `error`. Dispatch by `event`; do not assume every frame is a notification.

## 9. Recommended Frontend State Flow

Use the REST API for synchronization and the WebSocket for low-latency updates.

### On tutor login or app startup

1. Load the current authenticated user.
2. Fetch the first notification page.
3. Set the notification list from `data`.
4. Set the badge count from `metadata.unread_count`.
5. Connect the existing user WebSocket.

### When a WebSocket notification arrives

1. Parse the frame.
2. Ignore frames where `event !== 'notification'`.
3. Deduplicate by `payload.id`.
4. Add the notification to the beginning of the list.
5. Increment the unread count only if `payload.is_read === false` and the ID was not already present.
6. Show a toast or badge update if desired.

Example reducer-style logic:

```javascript
function receiveNotification(state, notification) {
  const alreadyExists = state.items.some((item) => item.id === notification.id);
  if (alreadyExists) {
    return state;
  }

  return {
    ...state,
    items: [notification, ...state.items],
    unreadCount: state.unreadCount + (notification.is_read ? 0 : 1),
  };
}
```

### When the user opens a notification

1. Navigate using `data.service_id` or `data.revision_id` where appropriate.
2. Call `PATCH /notifications/{id}/read/`.
3. Update the local item to `is_read: true`.
4. Decrease the local unread count, never below zero.

The read request should be sent before or alongside navigation. If it fails due to a temporary network error, keep the notification unread and retry later.

### When the user selects “Mark all as read”

1. Call `PATCH /notifications/read-all/`.
2. On success, set every local item to `is_read: true`.
3. Set the local unread count to `0`.

### On reconnect

1. Reconnect the WebSocket.
2. Fetch notifications again from REST, preferably using the first page.
3. Merge by notification ID.
4. Recalculate the unread count from the server response.

This protects against notifications created while the browser was closed or while the WebSocket was disconnected.

## 10. Approval Lifecycle

The backend approval sequence is:

```text
Admin approves pending revision
        |
        v
Service/revision change is applied
        |
        v
Notification row is created in the same database transaction
        |
        v
Transaction commits
        |
        +--> WebSocket notification is attempted if tutor is online
        |
        +--> Offline tutor receives it later through REST
```

If the approval transaction fails, the notification is not committed. If WebSocket delivery fails after commit, the notification remains available through REST.

The backend prevents approving a revision that is no longer pending. Repeating the approval request will return an error rather than create another approval notification.

## 11. Error Handling

Common responses:

| Status | Meaning |
| --- | --- |
| `401` | Missing, expired, or invalid authentication. Redirect to the normal login/token-refresh flow. |
| `404` | Notification does not exist or belongs to another user. Remove stale local references or refresh the list. |
| `422` | Invalid query parameter, such as `limit=0` or `offset=-1`. |
| `5xx` | Temporary backend failure. Keep local state and retry with backoff. |

For REST retries, avoid blindly creating local duplicates. The notification ID returned by the server is the stable identity.

## 12. Important Current Backend Notes

- Notification WebSocket delivery is best effort. REST synchronization is required.
- The current WebSocket endpoint is shared with chat and uses one connection per user in the backend process.
- The current WebSocket route uses the `{user_id}` path value to identify the connection. The frontend should always use the logged-in user's own ID.
- The current WebSocket handshake does not independently validate the bearer JWT. This is a backend security consideration for production hardening; it should not be treated as permission to connect as another user.
- Notification list pagination uses `offset` pagination, not cursor pagination.
- Notifications are not deleted by the current API.
- The current feature notifies approvals only. Rejection notifications can be added later using the same model and delivery contract.

## 13. Minimal TypeScript Types

```typescript
export type NotificationType =
  | "SERVICE_APPROVED"
  | "SERVICE_REVISION_APPROVED";

export interface ServiceApprovalData {
  revision_id: string;
  service_id: string | null;
  revision_type: "CREATE" | "UPDATE" | "DELETE";
}

export interface Notification {
  id: string;
  user_id: string;
  notification_type: NotificationType;
  title: string;
  message: string;
  data: ServiceApprovalData | null;
  is_read: boolean;
  created_at: string | null;
}

export interface NotificationListResponse {
  success: boolean;
  message: string;
  metadata: {
    total: number;
    unread_count: number;
    limit: number;
    offset: number;
  };
  data: Notification[];
}

export interface NotificationWebSocketFrame {
  event: "notification";
  payload: Notification;
}
```
